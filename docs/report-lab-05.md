**DEL-03 — контрольні питання.**

1. *Чому value з БД може залишатися недовіреним?* Бо в БД воно потрапило від користувача. Збереження і повернення через API не змінюють походження: це «збережене значення користувача», і для браузера воно лишається даними, які не можна вставляти як HTML.
2. *Source, transformation, sink у моєму flow?* Source — поле «Опис» на `/browser-lab.html`. Transformations — `POST /api/incidents` (валідація, `Trim`), збереження в `incidents.description`, `GET /api/incidents/{id}` → JSON `description`, `response.json()` у `load()`. Sink — `#description.innerHTML` (до), `#description.textContent` (після).
3. *Stored vs reflected vs DOM-based?* Stored — payload збережено на сервері, він виконується при пізнішому перегляді. Reflected — payload із запиту одразу повертається у відповіді й не зберігається. DOM-based — небезпечне перетворення відбувається в клієнтському JavaScript. Мій випадок одночасно stored (БД) і DOM-based (клієнтський `innerHTML`).
4. *Чому блокування `<script>` не усуває XSS?* Код виконується і без тегу `script`: через атрибути-обробники (`onerror`), інші теги, різні записи того самого. Мій marker не містить слова `script` взагалі. Виправляти треба sink, а не шукати «погані» слова.
5. *Коли textContent, а коли sanitizer?* Якщо поле — звичайний текст (як Description і коментарі), то `textContent`/`createElement`: HTML не потрібен узагалі. Sanitizer — лише коли продукт справді має приймати обмежений HTML, і тоді це перевірена бібліотека з мінімальним allowlist.
6. *Чому sanitizer не пишуть regular expression?* HTML має складну граматику, браузер «виправляє» некоректну розмітку, існує багато кодувань і контекстів. Regex неминуче пропускає варіанти, які браузер розбере як код. Потрібен парсер, що працює так само, як браузер.
7. *Origin?* Схема + host + port: `http://localhost:5080` і `http://localhost:4173` — різні origins через різні порти.
8. *Preflight?* Браузер сам перед «непростим» запитом надсилає `OPTIONS` із `Origin`, `Access-Control-Request-Method` і `Access-Control-Request-Headers`. Сервер відповідає дозволами `Access-Control-Allow-*`. Практично preflight я не досліджувала (рівень «Добре»).
9. *Хто оголошує і хто застосовує CORS?* Оголошує API заголовками відповіді (у мене — policy в `Program.cs`). Застосовує браузер: вирішує, чи віддати відповідь JavaScript сторінки іншого origin. Сервер запит не блокує.
10. *Чому curl читає відповідь, а browser script отримує CORS error?* Same-origin policy і CORS — правила браузера для коду вебсторінок. curl — не браузер, для нього їх немає. Запит у обох випадках доходить до API (у Network для 4174 видно GET 200), але браузер не віддає відповідь коду сторінки з 4174.
11. *Чому CORS не authorization і не CSRF-захист?* CORS не перевіряє, хто користувач і чи має він право, — це робить API (у мене `401`/`404`). Простий cross-origin запит доходить до сервера й може змінити стан навіть без дозволу CORS: браузер лише не покаже відповідь. Від CSRF потрібен окремий antiforgery-механізм (ЛР 6).
12. *Чому wildcard origin не поєднують із credentials?* Інакше будь-який сайт міг би від імені користувача з його cookie робити запити й читати відповіді. Тому специфікація забороняє `*` разом із `Allow-Credentials`: потрібен точний origin.
13. *Межа CSP?* CSP обмежує, звідки можна завантажувати й виконувати скрипти (наприклад, блокує inline-обробники), і зменшує наслідки XSS. Але вона не виправляє sink: дані все одно стають HTML, а за слабкої політики чи помилки конфігурації код виконається. Тому спочатку safe DOM, CSP — додатково (практика — рівень «Добре»).
14. *nosniff, Referrer-Policy, frame-ancestors?* `X-Content-Type-Options: nosniff` забороняє браузеру вгадувати тип вмісту (наприклад, виконувати текст як скрипт). `Referrer-Policy: no-referrer` не передає адресу сторінки стороннім сайтам. `frame-ancestors` у CSP забороняє вбудовувати сторінку у чужі фрейми (clickjacking). У моєму API перші два заголовки вже є (видно в curl).

**Межа backend validation.** Валідація ЛР 2 перевіряє довжину й обов'язковість. Вона не повинна і не може робити текст «безпечним HTML» для всіх майбутніх контекстів, тому захист реалізовано на межі інтерпретації — у DOM sink.

## Межі перевірки
Перевірено фактично: Description (основний flow), заміна обох `innerHTML` (опис і коментарі), прості CORS-запити, direct HTTP, 16 автотестів. Поза стендом лишилися: окремий seed-дослід коментаря, preflight, cookie-дослід, CSP/headers, автоматичний DOM-тест і URL-контекст (рівні «Добре»/«Відмінно»).

Знімки 18, 32–35 замість екрана терміналу зафіксували вікно браузера. Тому ці рисунки відтворено з транскрипту PowerShell (`Start-Transcript`), а не з екрана.
